Best practices for version management ​

The following is a best practice guide to configuration management / version management of Forms, Building Blocks and Reference Data.

In general terms we want the following to be true as our solution and related configuration evolves.

  1. We want data that has been captured on prior versions to be visible and editable if the context allows.
  2. We want to be able to query and view prior versions.
  3. We want new information/data to be captured using the latest published templates.
  4. We want all persisted data to medico-legally compliant (we know exactly what the healthcare professional was viewing at the time of capture).
  5. We want to be able to make changes in our development environment with minimal ceremony (breakages are acceptable), and minimal downstream inpact on configuration (such as workflow triggers).

The tables below represent how change should be managed for forms versions (and related building-block and reference data) that have been used in environments downstream from the development environment, where we need to consider the impact on forms and data, reports etc. Specifically we need to consider the impact on:

  1. Previously captured and completed forms - can we open read and PDF views.
  2. Draft forms - which are likely to be subsequently edited and completed.
  3. Submitted forms which can be amended.
  4. New forms created with the latest published template / versions.

Reference Data ​

Reference data is used when common value-sets sit externally to one or more building blocks. Reference data is a special case in terms of version management as it has a built-in capability to deprecate terms in the value-set meaning that some changes are possible without up-versioning. The table below shows what the recommended course of action is with any given change (🟢 - no need to up-version, ❗ - up-version required, ⚠️ - depends on exact circumstances).

ChangeConsequencesUp Version?
Remove (deprecate) an existing termExisting persisted form data will contain the deprecated term. As the term is deprecated the form will load and the deprecated term will be visible. If the form is submitted it will just be displayed. If the form is draft the term willl appear in the control it will be displayed, however if the value is deselected the end user cannot re-select it. New forms will not show the deprecated term as an option in the control.🟢 No
Minor change in term labelExisting term is modified (for instance to fix a typo). Draft, New or amended forms will show the new term. Saved forms will be saved with the label the user saw at the time of completing the form (for medico-legal compliance).🟢 No
Semantic changes in term labelExisting term is amended that changes its meaning in a material way. This will affect interpretation and reporting and is strongly discouraged, it is better to deprecate the existing term and add a new term. If you have to do it you will need to up-version.❗ Yes
Adding a new termYou are adding a new term to an exiting reference data value-set. All the other terms are left unchanged. Technically and data wise this is not a problem for AireFrame, however consideration of whether this is a breaking change is whether the new term is semantically similar or a subset of the existing terms. If it is, it is best to consider it a breaking change from an interpretation and reporting point for view and upversion.⚠️ Depends
Sub-divide a termRefine an existing coarse grained term into two or more, fine grained terms. This can be managed by relabling the original term and adding other terms (not recommded), or deprecating the original term and adding the new fine grained terms. From a reporting / interpretation perspective the change is large enough to warrant up-versioning.❗ Yes
